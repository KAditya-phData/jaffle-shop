# dbt docs generate

## What it does

Builds the dbt documentation website's data files: it copies the static index.html into target/, compiles the project (producing target/manifest.json, unless --no-compile is passed), and queries the warehouse's information schema / runs introspective operations to produce target/catalog.json (metadata about columns, tables/views for existing objects). It reads from the warehouse (information_schema lookups, and any introspective macros like run_query used during compilation) but does not create, modify, or drop any warehouse tables/views/rows.

## Effect on warehouse data

**Classification:** `writes-artifacts-only`

It only writes local artifacts (target/manifest.json, target/catalog.json, target/index.html). It performs read-only queries against the warehouse (metadata/information_schema lookups, plus any introspective Jinja macros like run_query() that execute during compilation) to populate catalog.json, but it never writes/creates/alters warehouse objects. Net effect on the warehouse: read-only. Net effect on disk/repo: writes artifact files only, not tracked project source files.

## Use in a dbt Cloud job

- **Can run as a step:** yes
- **Should run:** situational
- **Available as a job parameter/toggle instead:** Yes - dbt Cloud jobs and dbt-jobs-as-code expose this as a job-level toggle: the 'Generate docs on run' checkbox in the UI, and the generate_docs: true|false boolean field in jobs.yml (dbt-jobs-as-code schema, sibling to run_generate_sources and execute_steps).
- **Notes:** It CAN also be added directly as a command string inside execute_steps (e.g. "dbt docs generate"), and this is valid, but behaves differently from the toggle: as a regular run-step, a failure is a hard failure that can block/fail the job and any subsequent steps. As the 'Generate docs on run' toggle, dbt runs it after the listed steps and its failure does NOT fail the overall job as long as other steps succeeded (lenient/best-effort semantics). For dbt Cloud + dbt-jobs-as-code authoring, prefer the generate_docs job field over embedding it in execute_steps unless the user specifically wants doc-gen failures to be treated as blocking, or needs flags like --no-compile / --select which the toggle doesn't support.

## Info needed to add it (decision inputs)

| Field | Source | Notes |
|---|---|---|
| Whether to enable docs generation at all | `ask_user` | Purely a preference - ask if the user wants a docs site refreshed after this job, or if docs are already generated by another job (e.g. a dedicated nightly docs job) to avoid duplication. |
| generate_docs boolean value in jobs.yml | `have` | Once the user says yes/no, the agent just sets generate_docs: true/false at the job level - no additional lookup needed. |
| Whether to instead add as an explicit dbt docs generate step in execute_steps (with flags like --no-compile or --select) | `ask_user` | Only needed if the user wants non-default behavior (e.g. skip compile, scope to a subset) that the simple toggle doesn't support - the toggle takes no flags. |
| Environment/account/project IDs for the job | `memory` | Same job-level IDs already resolved for the rest of the job spec (account_id, environment_id, project_id) - not specific to this command. |
| Warehouse credentials/connection | `have` | Uses the job's existing environment connection; no separate credential needed since it's the same connection as other steps in the job. |

> `have` = agent already knows it · `memory` = pull from stored account/env/group defaults · `ask_user` = must ask.

## Options / flags

### `--no-compile`
- **Purpose:** Skips the project-compile step (which produces manifest.json) before generating catalog.json, so docs generate uses whatever manifest.json already exists (e.g. from an earlier dbt run/dbt compile step in the same job) instead of recompiling.
- **Data effect:** Still read-only on the warehouse for the catalog step (information_schema queries). Reduces warehouse reads by skipping compilation, since introspective macros in models won't be re-executed. If no manifest.json already exists from a prior step, compiled_code will be missing/stale in the docs.
- **Info needed:** Whether a prior step in the same job (run/build/compile) already produced an up-to-date manifest.json in target/. This is a job-design detail - ask the user or infer from the rest of execute_steps.
- **When to include:** Include only when dbt docs generate runs as its own explicit command step immediately after a dbt run/dbt build step that already compiled the project - saves redundant compile time. Skip (use the default toggle instead) if docs generation is the first/only compile-producing step in the job, since accurate compiled SQL and lineage need the compile step.
- **Good vs bad:** Good: in a job that already runs dbt build then a manual dbt docs generate --no-compile step, avoids a second full re-compilation, cutting run time. Bad: using --no-compile as the very first/only command in a job with no prior compile step, resulting in an empty or stale manifest.json and broken 'compiled SQL' tab in the docs UI.

### `--select / --exclude (node selection)`
- **Purpose:** Scopes which resources are included in catalog.json metadata (and, if compiling, in manifest.json), e.g. generating docs for only a subset of models.
- **Data effect:** No change to warehouse write behavior; still read-only. Only changes which existing warehouse objects get metadata queried/documented.
- **Info needed:** The model/selector syntax to scope to, if the user wants partial docs instead of the whole project - ask the user only if they've indicated they don't want full-project docs.
- **When to include:** Skip by default - full-project docs generation is standard for scheduled jobs. Only use for large monorepos where full docs generation is too slow/expensive and the user explicitly wants a scoped subset.
- **Good vs bad:** Good: scoping docs to a subdomain's models in a huge monorepo to cut generation time. Bad: routinely scoping docs generation in a normal-sized project, which just fragments the catalog and confuses anyone browsing lineage for excluded models.

### `--target-path`
- **Purpose:** Overrides where target/manifest.json, catalog.json, and index.html get written.
- **Data effect:** No warehouse effect; purely a local filesystem path change for artifacts.
- **Info needed:** Custom path, only if the user's project has non-default artifact-path conventions (rare) - check dbt_project.yml target-path or ask only if relevant.
- **When to include:** Skip by default; dbt Cloud manages artifact paths/display automatically. Only relevant for custom CI pipelines outside dbt Cloud's native docs viewer.
- **Good vs bad:** Good: setting it in a custom non-dbt-Cloud CI pipeline that publishes docs to a specific static-hosting path. Bad: setting it inside a dbt Cloud job, where dbt Cloud's docs viewer expects the default target/ path and a custom path can break the built-in 'View Docs' link.

## Best practices

- **Use the job-level 'Generate docs on run' / generate_docs: true toggle instead of adding dbt docs generate as a raw execute_steps command, when you simply want docs refreshed after a successful build.**
  - Why: The toggle runs after the main steps with lenient failure handling - a docs-generation hiccup won't fail the whole job/pipeline, whereas a manual command step is a hard link in the chain that can block downstream steps or mark the job failed.
- **Only enable docs generation on one canonical job per environment (e.g., the main production/nightly build job), not on every CI or ad-hoc job.**
  - Why: Docs generation adds compile + catalog-query overhead on every run; running it redundantly across many jobs against the same environment wastes time/warehouse queries for a docs site that only needs to reflect the latest successful state once.

## Anti-patterns

- **Adding dbt docs generate as an explicit step in a short-lived CI/PR job (e.g., a job that runs dbt build --select state:modified+) just to 'keep docs fresh'.**
  - Why: CI jobs run on ephemeral/partial builds and often against transient schemas; generating and publishing docs there produces a doc site reflecting a non-production, partial subset of models, misleading anyone browsing the catalog.
- **Using --no-compile as the only/first command in a job without any preceding compile-producing step, to 'save time'.**
  - Why: Without an existing manifest.json, catalog.json will be generated against stale or missing model metadata, resulting in a docs site with missing compiled SQL and possibly incorrect lineage - the time saved isn't worth the broken artifact.
